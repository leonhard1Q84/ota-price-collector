## 结论等级

写方案或排障时区分三种表述：

- **已验证事实**：在本地组合测试、源码检查或真实部署运行中直接观察到。
- **高风险因素**：与问题有明确相关性或符合 DataDome/浏览器工作方式，但不能表述成每次必然触发。
- **未知项**：Klook 和 DataDome 没有公开完整决策模型，不能反推精确阈值。

当前可作为工程基线的结论是：有头 Playwright、独占持久 Profile、浏览器显式固定代理、完整域名同出口、长生命周期复用和保守限频的组合已经稳定通过本地观察，并在现有 Klook 程序真实部署后持续运行正常。这是“目前验证有效的低风险组合”，不是绕过风控的保证。

## .com 与 .cn 的决定因素

`.com` 和 `.cn` 不是只由当前 IP 国别决定，而是 Klook 网络定位、站点路由 Cookie 和 Profile 历史状态共同决定。

已验证现象：

- Klook `.com` 在无 VPN 的国内网络也可以访问，说明“必须使用国外 IP 才能打开 `.com`”不成立。
- Profile 已写入国际站偏好后，即使切回国内 IP，后续仍可停留在 `.com`。
- 某个 Chrome Profile 访问过 `.cn` 后，后续即使更换网络出口，也可能持续从 `.com` 跳回 `.cn`。
- 定向删除 `klk_rdc` 并规范化 `.klook.com` 域的 `klk_ps=1` 后，可以强制恢复并保持国际站路由，而无需删除整个 Profile。
- 页面语言从英文改成中文并不必然触发 `.cn` 跳转；`en-US` 不是国际站控制的必要条件。

现有稳定程序的源码进一步确认了一个具体污染模式：访问国内站后可能留下 `klk_rdc=CN`，同时存在 host-only 的旧 `klk_ps`。如果程序只新增一个 `.klook.com` 的 `klk_ps`，Chrome 可能同时发送新旧两个同名 Cookie，Klook 仍选择 `.cn`。因此必须先检查全部同名 Cookie，发现不规范时全部定向清除，再写入唯一规范值。

工程含义：

1. 不能只把 URL 写成 `.com`。
2. 不能只更换 VPN 节点。
3. 不能用全量删除 userdata 处理每次跳转。
4. 必须在每次导航前幂等修复路由 Cookie，并在导航后验证最终域名。

## Cookie 与客源地的职责边界

下面三类状态容易被混淆：

| 状态 | 已知用途 | 典型值 |
| --- | --- | --- |
| `klk_ps` | Klook 站点偏好/国际站路由 | `.klook.com`、`/`、`1` |
| `klk_rdc` | 重定向路由状态；国内站污染时可出现 | `CN` |
| `transfer-user-residence` | 租车用户居住地/客源地 | `1_HK`、`1_KR` 等 |
| `x-klook-user-residence` | 请求层的客源地 Header | `HK`、`KR` 等 |

运营使用的 `user-residence-switcher` 插件源码会把 `transfer-user-residence=1_<国家码>` 同时写到 `.klook.com` 和 `.klook.cn`。这说明它的核心作用是切换租车业务的用户居住地，而不是决定访问哪个顶级域。现有 `price-data` 和 Klook 程序还会设置 `x-klook-user-residence` Header，它同样服务于客源地/库存或报价语义。

所以：

- 控制 `.com/.cn`：处理 `klk_ps`、`klk_rdc`，并验证最终域名。
- 控制客源地：设置业务要求的 `transfer-user-residence` Cookie 或 `x-klook-user-residence` Header，并核对 Klook 实际接口语义。
- 不要因为设置了客源地就假设站点域名已经正确，也不要用国际站 Cookie 替代业务客源地。

## VPN、Clash、DIRECT 与实际出口

系统显示“VPN 已连接”不等于浏览器每一个请求都经过所选节点。

一次已完成的诊断曾观察到以下组合：

- Clash 运行在规则模式，TUN 未开启。
- `www.klook.com` 被解析到中国侧 WAF 地址，并命中 `GEOIP,CN -> DIRECT`。
- Klook 主站走中国直连，而 DataDome 请求走日本代理节点。
- 同一机器同时存在国内 IPv4、国内 IPv6 和代理出口。

这解释了为什么“明明开了日本 VPN，Klook 仍看到中国出口”：域名先经过本地或代理 DNS 得到中国 IP，规则再按目标 IP 判定为中国地址，最终走 `DIRECT`。与此同时，另一个风控域名可能命中代理规则。

`DIRECT` 的精确定义是“这个连接绕过代理节点，使用操作系统的本地网络路由”。它在数据出口上通常等价于该请求未走代理，但“Clash 保持运行且命中 DIRECT”和“彻底关闭 Clash/VPN”并不完全等价，因为前者仍可能影响：

- DNS 解析与缓存；
- 域名嗅探和规则判断；
- 系统代理设置；
- IPv4/IPv6 选择；
- 其他域名的代理路径。

全局模式通常能减少规则分流造成的不一致，但仍不是程序级保证：代理应用可能有绕过列表、DNS 特例、IPv6 直连或失效回退。长期程序应把固定代理显式传入浏览器，再在该代理程序中保证相关域名使用同一策略组。

## DataDome 为什么要求出口一致

DataDome 是 Klook 集成的第三方 Bot/风险控制服务，不是浏览器本地生成的页面。访问 Klook 时，除 Klook 主站和业务 API 外，浏览器还会向 DataDome 相关服务发出请求；验证或过渡内容常出现在 `captcha-delivery.com` 的 Frame，其他脚本或信号可能使用 `datadome.co` 及其子域。

因此一个“页面访问”实际上至少包含两组服务之间的协作：

1. Klook 主站/业务 API 接收请求并关联会话。
2. DataDome 获取同一会话的网络、Cookie、浏览器和行为信号，返回自动过渡、滑块或拦截判断。

如果 Klook 主站使用中国直连 IP，而 DataDome 使用日本代理 IP，服务端看到的是同一个浏览器会话在短时间内跨国家/跨出口出现。地区、自治系统、IP 信誉和会话连续性互相矛盾。**在我们当时的重复测试中，这种确定的出口不一致会稳定进入 L2 硬拦截，而不是只提高 L1 概率。**

可能的技术原因是：Klook 首次请求产生的 DataDome 会话、挑战标识和网络身份需要在后续 `captcha-delivery.com`/`datadome.co` 请求中保持一致；后续请求突然换成另一个国家/IP，会让同一挑战的来源身份无法闭环。这个底层机制符合测试现象，但 DataDome 没有公开完整校验细节，因此应将“稳定触发 L2”限定为我们的实测工程结论，不表述成 DataDome 面向所有网站和所有版本的官方保证。

“同出口”应覆盖：

- `klook.com` 及实际使用的 Klook 子域；
- `captcha-delivery.com`；
- `datadome.co` 及其实际子域；
- DNS 解析路径；
- IPv4 与 IPv6；
- 页面主导航、Frame、XHR/fetch 和静态脚本请求。

工程上必须把 Klook 与 DataDome 出口不一致视为不可运行配置：启动前或预检阶段发现不一致就直接失败，不要先访问 Klook“看看会不会被拦截”。出口一致是避免该类稳定 L2 的必要条件，但不是“永不触发风控”的充分条件；即使出口完全一致，DataDome 仍可能综合 IP 信誉、访问频率、浏览器指纹、Cookie 连续性、页面行为和历史挑战结果触发 L1 或其他 L2。

## 三级页面现象与两级人工风控

实际需要识别三个 DataDome 相关现象：

DataDome 没有公开 Klook 场景下的完整评分模型和阈值，因此无法给出“第几次访问”或“每分钟多少次”必然触发 L1/L2 的公式。更准确的理解是：网络出口、IP 信誉、Profile/会话连续性、浏览器信号和访问行为共同形成风险评分。风险升高但仍允许证明真人时通常进入 L1；风险更高、信号冲突更严重，或挑战出现后仍持续异常请求时，可能进入 L2。唯一需要在当前方案中单独提升为硬约束的是：我们已经稳定复现 Klook 与 DataDome 出口不一致会进入 L2，因此不能把它仅列为普通概率因素。

### 自动过渡页（AUTO_INTERSTITIAL）

页面可能先出现 HTTP 403 或 `captcha-delivery.com/interstitial`，随后自动恢复正常 `.com`。这是短暂过渡，不等同于 L2。

处理方式：保留页面，短时间轮询状态，不刷新。只有页面稳定回到 `.com` 且最终主导航状态健康后才继续。

### 一级风控（L1_SLIDER）

表现为滑块或“请完成人机验证”。验证内容可能位于 `captcha-delivery.com/captcha` Frame 中。

#### 什么时候可能触发 L1

L1 通常表示“当前访问可疑，但 DataDome 仍允许通过人工验证恢复”。以下情况会提高进入 L1 的概率：

- **短时间请求过快或累计请求过多**：连续 `goto`、刷新、快速切换日期/客源地、滚动或翻页触发大量业务请求，都会让同一出口的行为密度升高。
- **同一出口存在并发访问**：多个 Page、进程、worker，甚至程序浏览器和人工浏览器同时通过同一 IP 访问 Klook，风险按出口聚合后可能先要求验证。
- **会话连续性较弱**：频繁删除 userdata、使用临时/无痕 Profile、每次查询新建 Context、频繁开关浏览器，使 Cookie、缓存和历史会话无法形成稳定连续性。
- **出口 IP 已积累风险**：该 IP 刚经历压力测试、被多个自动化任务共用、信誉较低，或先前的挑战尚未完成时，即使当前单次访问不快也可能出现 L1。
- **浏览器和行为信号组合异常**：自动化特征、非常机械的固定节奏、页面尚未稳定就继续操作等因素单独未必触发，但和高频、临时 Profile、出口 IP 已积累风险等因素叠加时风险更高。Klook/DataDome 跨域出口不一致不放在这一类 L1 概率因素中，而按下文已经稳定复现的 L2 硬错误处理。

已直接观察到的是：压力测试持续请求后，程序浏览器和同出口的本地浏览器都出现了 L1；在本地浏览器完成人工验证后，程序浏览器中的验证也可能随之解除。这说明出口 IP 或出口级风险票据确实参与判断，但不能简化为“L1 只按 IP”，因为 Profile Cookie、会话和浏览器信号仍会参与。

以下单一条件不能被写成“必然触发 L1”：使用 Playwright、使用全新 Profile、使用国内 IP、页面语言为中文或偶发一次 403。测试中，普通 Playwright 配合有头 Chrome、全新但持久的 Profile、稳定同出口和保守频率，可以从零开始持续正常访问。

处理方式：暂停该 worker 的所有请求，保持当前有头浏览器和 Profile，通知人工在原页面完成。不要关闭、刷新、自动拖动或新建临时 Profile。人工完成后重新确认页面为健康 `.com` 才恢复。

### 二级风控（L2_HARD_BLOCK）

表现为明确的“访问存在风险，已被拦截”“建议使用非自动化工具”或英文 hard-block 文案。这是硬拦截，不是滑块未完成，也不是一个普通可重试 403。

#### 什么时候可能触发 L2

L2 通常表示“当前会话或出口的风险已经高到不再提供普通人工挑战，而是直接拒绝访问”。以下情况比单纯出现 L1 更容易触发或升级到 L2：

- **Klook 与 DataDome 出口不一致（本环境已稳定复现）**：主站使用中国直连，而 `captcha-delivery.com`/`datadome.co` 使用日本等其他出口，或 DNS、IPv4/IPv6 分流导致两侧实际 IP 不同，会稳定进入 L2。程序必须在访问前保证同出口，发现不一致直接判定环境不可用。
- **L1 出现后仍继续发请求**：不暂停其他 Page/worker、反复刷新验证页、连续重新 `goto`，会把“等待人工证明”升级成“持续异常访问”。
- **自动或反复失败地处理挑战**：程序自动拖动滑块、重复提交失败轨迹、刷新或重建页面试图跳过挑战，会产生比“停留等待人工”更强的异常信号。
- **同一会话中频繁切换出口**：查询过程中切换代理国家/节点，或连接在 IPv4 与 IPv6 的不同出口之间跳变，会让已经建立的会话网络身份失去连续性。它与“不同域名同时分流”是两种问题，但同样更接近 L2 风险。
- **高频、并发和弱 Profile 连续性叠加**：临时 Profile、频繁重启、多实例并发、快速重试中的任意一项未必单独导致 L2，但同时出现时风险显著高于普通 L1 场景。
- **出口 IP 本身已处于高风险状态**：共享代理已被大量访问、刚经历未处理的 L1/压力测试、信誉很差或已进入拦截名单时，新 Profile 的第一次访问也可能直接 L2。
- **请求与浏览器会话明显不一致**：绕过页面直接高频调用业务 API、缺少或混用当前浏览器会话所需的 Cookie/Header、页面与接口来自不同出口，可能形成更强的自动化或会话伪造信号。
- **对硬错误进行密集普通重试**：持续 403、未知敏感页面或连续 429 后仍按秒级频率重试，会继续积累风险；429 本身仍是限流，只有伴随上述行为或明确拦截证据时才归入 L2。

此前测试中，L2 曾与临时/新建会话、路由不一致、快速重试等组合同时出现；另一台部署机器删除 userdata 后也曾在首次访问直接 L2。但这些测试同时存在机器环境、实际 DNS/出口、IP 历史和启动方式差异，因此只能证明这些是高风险组合，不能证明“删除 Profile”或“普通 Playwright”单独必然触发 L2。

L2 不一定先经过 L1。若出口 IP 已积累较高风险，或首次请求就同时暴露严重的出口/会话冲突，DataDome 可能直接返回硬拦截。反过来，出现 L1 后立即停止请求并由人工完成验证，也不意味着必然升级到 L2。

处理方式：立即熔断该会话/worker，保留现场、截图和 Profile，停止导航。排查出口一致性、代理信誉、频率和 Profile 状态后由人工决定恢复；禁止普通三次刷新。

#### L1 与 L2 的触发差异

| 风险场景 | 更可能表现为 L1 | 更可能表现为 L2 |
| --- | --- | --- |
| 访问频率升高 | 首次超过动态风险阈值，系统要求人工证明 | 已出现挑战仍持续高频或多 worker 继续请求 |
| Klook/DataDome 出口不一致 | 不按普通 L1 诱因处理 | 本环境已稳定复现 L2；发现后应在访问前直接阻断 |
| Profile 连续性 | 新/临时 Profile 导致信任不足 | 临时 Profile + 高频 + 重启/刷新 + 高风险出口叠加 |
| 出口 IP 历史 | IP 风险升高但仍允许验证 | IP 已处于高风险/拦截状态，可能首次访问就硬拦截 |
| 挑战后的行为 | 原地停止并等待人工处理 | 自动拖动、重复失败、刷新、重建会话或绕过挑战继续请求 |
| API 行为 | 页面正常产生接口请求，偶发节奏异常 | 直接高频调用、会话/Header/出口明显不一致 |

除表中已经注明为本环境稳定复现的“Klook/DataDome 出口不一致”外，这张表表示概率上的差异，不是 DataDome 的公开规则。实际页面状态仍须依据页面、Frame URL 和明确文案分类，不能只根据一般诱因反推，也不能把一个裸 HTTP 403 直接判成 L2。

仅凭 HTTP 403 或页面中的 DataDome 诊断 ID 无法区分三级现象。滑块页本身也可能返回 403，自动过渡也可能返回 403。分类必须结合 Frame URL 和明确页面文案。

## Profile 为什么重要

浏览器 Profile（Playwright 的 `user_data_dir`）不只是 Cookie 目录，还持久化 LocalStorage、IndexedDB、缓存、Service Worker、站点权限、浏览器偏好、DataDome 会话状态和 Klook 地区状态。它提供跨查询、跨浏览器重启的连续性。

稳定用法：

- 每个 worker 有一个固定目录；长期复用。
- 同一个目录不能被两个 Chrome/进程同时打开；使用文件锁。
- 浏览器正常退出后保留目录，下次继续使用。
- 每台部署机器独立初始化；不要复制个人浏览器 Profile。
- 日常问题优先定向清理 `klk_ps/klk_rdc` 等已知污染，不删除 DataDome 状态。

删除整个 Profile 会同时丢失有害状态和有价值的会话连续性，不能作为默认修复。复制 Profile 也不适合作为长期部署方案：Cookie 可能与机器、系统加密或出口历史有关，复制后可能失效或增加风险。

“临时 Profile 必然触发 L2”也不成立。测试中从零创建的新持久 Profile 曾持续正常访问；另一台机器删除 userdata 后却立即 L2。这说明 Profile 新旧不是唯一变量，机器环境、实际出口、代理规则、浏览器版本、启动方式、IP 风险历史和访问节奏都可能不同。

临时/无痕 Context 仍是高风险工程选择，因为它每次丢失连续性，并常与频繁开关浏览器、不同二进制、快速重试等信号叠加。刚下载的普通 Chrome 虽然也是新 Profile，但通常有人类启动节奏、稳定网络、标准 Chrome channel，不能只用“都是新上下文”类比。

## 访问频率与浏览器生命周期

一级验证的精确触发阈值未知。下面列的是可能推高 L1 风险评分的行为因素；不包含 Klook/DataDome 出口不一致，后者已在我们的测试中稳定复现 L2，并作为环境硬错误单独处理。

- 短时间连续导航、刷新或翻页；
- 多 Page/多进程共享一个出口并发访问；
- 每个 URL 都新建和关闭浏览器；
- 失败后立即刷新或重新创建临时 Profile；
- 低信誉或已积累风险的代理 IP。

现有稳定程序采用串行访问、完整查询后至少 30 秒静默并增加 0–5 秒抖动，同时在同一任务批次内保持浏览器长生命周期。业务层已有的页面加载等待、滚动间隔和 URL/日期/客源地之间的额外等待继续保留。

浏览器“永久不关闭”也没有必要。合理边界是：有待处理任务时持续复用；队列确认空闲后正常关闭 Context；下次任务重新启动同一持久 Profile。

## Too Many Requests 与 DataDome 的区别

HTTP 429 或页面明确显示 `Too Many Requests` 代表服务端限流，不能仅凭这一现象判定为 DataDome L1/L2。它通常可以通过冷却后重试恢复。

建议动作：

1. 暂停该 worker/出口的新查询。
2. 有 `Retry-After` 时优先遵循。
3. 没有时使用 60、120、240 秒长退避。
4. 最多重试 3 次，仍失败则结束当前查询并记录限流。
5. 保持同一 Profile；不要为清除 429 重启浏览器。
6. 把冷却时间存放在浏览器生命周期之外，避免浏览器崩溃或重启后立即继续请求。

如果 429 同时伴随 captcha Frame 或明确 hard-block 文案，按更严格的 L1/L2 处理，而不是只按限流处理。

## 常见误解

- **Playwright 就是无头浏览器**：错误。Playwright 是自动化框架，可启动有头或无头浏览器。当前稳定基线使用 `headless=False`。
- **普通 Playwright 必然 L2，CDP 才安全**：错误。当前稳定方案就是普通 `launch_persistent_context`；CDP 只是连接既有浏览器的协议方式，不是风控绕过能力。
- **Selenium 可以自动拖动滑块所以更安全**：错误。框架替换不会取消验证码含义；自动拖动属于自动处理挑战，不在方案范围内，也可能升级风险。
- **无痕模式能避免风控**：错误。无痕会丢失连续状态，不能改变 IP 信誉或出口不一致。
- **国内 IP 必然跳 `.cn`**：错误。已验证国内 IP 在国际站偏好正确时可持续访问 `.com`。
- **换成英文或 `en-US` 就是国际站**：错误。语言影响 UI，不是顶级域路由的主控制量。
- **VPN 开全局就无需程序配置代理**：不可靠。长期程序需要浏览器级显式代理和出口验收。
- **直接请求数据 API 就没有页面风控**：不可靠。业务 API 仍可能依赖 DataDome Cookie、会话、签名、Header 和限流，直接调用也可能触发风险。
- **403 就是二级风控**：错误。必须区分自动过渡、L1 和 L2。
- **遇到 `.cn` 就删除 userdata**：不推荐。先定向修复路由 Cookie并保留其他 Profile 状态。

## 症状诊断矩阵

| 症状 | 优先检查 | 不要先做 |
| --- | --- | --- |
| `.com` 立刻跳 `.cn`，换节点也不变 | `klk_rdc=CN`、重复/host-only `klk_ps`、最终域名和 `.cn` 导航请求 | 删除整个 Profile |
| 开 VPN 后主站仍像中国出口 | Clash 规则、DNS 结果、`GEOIP,CN -> DIRECT`、IPv6、浏览器是否显式代理 | 只反复换节点 |
| Klook 正常而验证 Frame 异常 | Klook、`captcha-delivery.com`、`datadome.co` 是否同出口 | 刷新验证页 |
| 每次启动都出现滑块 | Profile 是否临时、浏览器是否频繁开关、出口风险、请求频率、同出口并发 | 自动拖滑块或改 Selenium |
| 明确二级拦截页 | 立即停止；保留截图、Profile、最终 URL；核对出口、IP 信誉和近期压力 | 普通三次刷新 |
| 只有 429/Too Many Requests | `Retry-After`、近期请求速率、同出口 worker 数、冷却是否跨重启保存 | 删除 Profile或立即重启 |
| 新 Profile 在一台机器正常、另一台 L2 | 实际出口/DNS、浏览器 channel/版本、代理规则、IP 历史、启动参数和节奏 | 断言“新 Profile 必然安全/危险” |
